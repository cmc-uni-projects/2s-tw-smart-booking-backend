# Multi-language (i18n): frontend + backend

Vietnamese (default) and English everywhere: every frontend page (customer, owner, admin, partner), API messages, validation errors, in-app notifications and emails. Prices stay in VND. Database content that people type (hotel names, descriptions, reviews) is not translated.

## Which language is used where

| What | Language comes from |
|---|---|
| UI text | the picker (stored in `localStorage.lang`); after login, the account's `preferredLanguage` |
| API responses (errors, success messages, validation) | the request's `Accept-Language` header (axios sends the UI language) |
| Notifications | the **reader's** request language: stored as key + params, rendered on read |
| Emails | the **recipient's** `users.preferredLanguage`; unknown address → current request language → Vietnamese |
| Audit log texts | stored as a deferred key (`i18n:<key>:<json args>`), rendered on read |

`users.preferredLanguage` (`vi`/`en`, Liquibase `0003`) is set at registration from `Accept-Language` and changed by `PUT /api/v1/user-details/language {"language":"en"}`, which the frontend calls whenever a signed-in user switches language (`src/i18n/language.js`). `/auth/login` and `/auth/me` return it, and the frontend applies it after login.

## Backend

| Piece | Where |
|---|---|
| Bundles (UTF-8, MessageFormat) | `src/main/resources/i18n/messages{,_en}.properties`: errors, API messages, validation, notifications, audit, chat; `i18n/emails{,_en}.properties`: email subjects + template texts |
| Locale resolver (vi default, en) | `i18n/I18nConfig.java` |
| Translate | `Messages.t(key, args...)` (request locale), `t(locale, key, args...)`, `Messages.of(exception)` for controller catch blocks |
| Recipient locale | `UserLocales.of(user)`, `forEmail(email)`, `ofAccount(email)` |
| Errors | `throw new BadRequestException("error.booking.notFound", id)`: `AppException` subclasses carry key + args + HTTP status; `GlobalExceptionHandler` answers `{ success:false, message:"<translated>", code:"<key>" }` |
| Validation | DTO annotations use `{validation.x.y}`; the 400 response `data` maps field → translated message, `code: "error.validation"` |
| Notifications | `notificationService.sendNotification(userId, type, relatedId, "notification.booking.confirmed", args...)` stores `titleKey`/`messageKey`/`params` (JSON); title/message columns hold a copy in the recipient's language as a fallback |
| Emails | `EmailServiceImpl` builds `new Context(recipientLocale, vars)`; templates use `th:text="#{email.x.y}"`, sentences with markup use `th:utext="#{key(${#strings.escapeXml(var)})}"` (escape every parameter!) |

MessageFormat rules (because `spring.messages.always-use-message-format=true`): placeholders `{0}`, numbers `{0,number,#,##0}`, and write an apostrophe as `''`.

**Clients branch on `code`, never on `message`.** The message changes with the language; the code is stable.

## Frontend

| Piece | Where |
|---|---|
| Init, language list, `<html lang>` | `src/i18n/index.js` (`SUPPORTED_LANGUAGES`) |
| Switch language (+ save to account) / apply after login | `src/i18n/language.js` (`changeLanguage`, `applyUserLanguage`) |
| Translations | `src/i18n/locales/{vi,en}/<ns>.json`: `common, layout, home, search, hotel, booking, promotion, auth, profile, about, help, owner, admin, partner` |
| date-fns locale | `src/i18n/dateLocale.js` |

```jsx
const { t } = useTranslation("booking");
t("pay.title");                              // booking:pay.title
t("owner:CheckOutModal.confirmCheckOut");    // explicit namespace (owner/admin files use this form)
t("common:nights", { count: 3 });           // interpolation + plurals
<Trans t={t} i18nKey="pay.tip" components={{ b: <strong /> }} />
```

Outside components (helpers, module-level option lists, yup schemas) use `import i18n from "@/i18n"` **lazily**, so the text follows language switches:
- in a function: `i18n.t("admin:x.y")`
- in a module-level object: `get label() { return i18n.t("owner:Step2_Amenities.pool"); }`
- yup: `.required(() => i18n.t("owner:AddPropertyPage.enterTheAddress"))`
- default props: `title = i18n.t(...)` (the hook's `t` does not exist yet in the parameter list)

Owner/admin/partner keys are grouped by file: `<ns>:<FileName>.<camelCaseOfEnglish>`. Other rules: proper nouns and Vietnamese-only data stay as-is with `// i18n-ignore` (or an `i18n-ignore-start … i18n-ignore-end` block); `console.*` messages are plain English.

## Checks

```bash
# frontend: key parity, every literal t() key exists, no hardcoded Vietnamese in translated folders
npm run i18n:check
# backend: vi/en key parity + valid MessageFormat; every email template renders in both languages
./mvnw test -Dtest='MessageBundlesTest,EmailTemplatesTest'
```

## Adding a language
Frontend: add `{ code, label, flag }` to `SUPPORTED_LANGUAGES`, copy `locales/en` to `locales/<code>`, add a date-fns locale. Backend: add the `Locale` to `I18nConfig.SUPPORTED`, add `messages_<code>.properties` and `emails_<code>.properties`, and add the code to the two parameterized tests. The checks enforce key parity.
